# 5.4. Estándares en Servicios (Idiomas de Internet)

Para que dos computadoras hablen, necesitan un protocolo común.
En los 90s era XML, hoy es JSON, mañana será Binary.

---

## 1. SOAP (Simple Object Access Protocol) - El Abuelo Estricto

Nacido en Microsoft (1998). Es un protocolo basado en XML.

### 1.1 Características
*   **Verboso:** Todo es un sobre (`<Envelope>`) con cabeceras (`<Header>`) y cuerpo (`<Body>`).
*   **Estricto:** Usa **WSDL** (Web Services Description Language) para definir EXACTAMENTE qué datos entran y salen.
*   **Seguro:** Tiene **WS-Security** (Encriptación y firma digital a nivel mensaje, no solo HTTPS).
*   **Transaccional:** Soporta **WS-AtomicTransaction** (ACID distribuido).

### 1.2 Ejemplo de Request
```xml
POST /InStock HTTP/1.1
Host: www.example.org
Content-Type: application/soap+xml; charset=utf-8

<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope">
  <soap:Header>
  </soap:Header>
  <soap:Body>
    <m:GetStockPrice xmlns:m="http://www.example.org/stock">
      <m:StockName>IBM</m:StockName>
    </m:GetStockPrice>
  </soap:Body>
</soap:Envelope>
```

### 1.3 ¿Cuándo usarlo hoy?
*   Bancos (Sistemas Core Banking).
*   Gobierno (Facturación Electrónica).
*   Integraciones Legacy.

## 2. REST (Representational State Transfer) - El Estándar Actual

Tesis doctoral de Roy Fielding (2000). No es un protocolo, es un **Estilo Arquitectónico**.

### 2.1 Principios
1.  **Recursos:** Todo es una URL (`/users/123`).
2.  **Verbos HTTP:** `GET` (Leer), `POST` (Crear), `PUT` (Reemplazar), `PATCH` (Editar), `DELETE` (Borrar).
3.  **Stateless:** El servidor no guarda "sesión" entre requests. Cada request lleva su Auth Token.
4.  **Representación:** Puedes pedir el mismo recurso en JSON o XML (`Accept: application/json`).

### 2.2 Richardson Maturity Model (Niveles de REST)
*   **Nivel 0 (The Swamp of POX):** Usas HTTP como túnel. Todo es `POST /apiService`.
*   **Nivel 1 (Recursos):** Tienes URLs distintas `/users`, `/products`.
*   **Nivel 2 (Verbos HTTP):** Usas `GET` para leer y `DELETE` para borrar (No `POST /deleteUser`).
*   **Nivel 3 (HATEOAS):** La respuesta incluye links a qué hacer después.

### 2.3 Ejemplo HATEOAS
```json
{
  "id": 123,
  "balance": 50.00,
  "links": [
    { "rel": "deposit", "href": "/accounts/123/deposit" },
    { "rel": "withdraw", "href": "/accounts/123/withdraw" }
  ]
}
```

## 3. GraphQL (Graph Query Language) - El Retador de Facebook

Diseñado por Facebook en 2012 para su App móvil.

### 3.1 El Problema de REST (Overfetching/Underfetching)
*   **REST:** Pides `/users/1`. Te devuelve 50 campos (Nombre, Email, Dirección...). Solo querías el Nombre. (Overfetching).
*   **REST:** Quieres los amigos del usuario. Tienes que hacer OTRO request a `/users/1/friends`. (Underfetching).

### 3.2 La Solución (Un solo Endpoint)
Envías una consulta ("Query") describiendo EXACTAMENTE qué quieres.

```graphql
query {
  user(id: "123") {
    name
    friends {
      name
      city
    }
  }
}
```

Respuesta (JSON exacto):
```json
{
  "data": {
    "user": {
      "name": "Jesús",
      "friends": [
        { "name": "Ana", "city": "CDMX" }
      ]
    }
  }
}
```

### 3.3 Schema & Types
GraphQL es fuertemente tipado.
```graphql
type User {
  id: ID!
  name: String!
  age: Int
  friends: [User]
}
```

## 4. gRPC (Remote Procedure Call) - La Bestia de Google

Diseñado por Google (Stubby). Usa **HTTP/2** y **Protocol Buffers**.

### 4.1 Binario vs Texto
*   REST/JSON envía texto: `{"name": "Jesús"}` (18 bytes).
*   gRPC/Protobuf envía binario: `0A 05 4A 65 73 FA 73` (7 bytes).
*   **Resultado:** gRPC es 7x a 10x más rápido que REST.

### 4.2 Protocol Buffers (.proto)
Defines el contrato en un archivo neutro.
```protobuf
syntax = "proto3";

service Greeter {
  rpc SayHello (HelloRequest) returns (HelloReply) {}
}

message HelloRequest {
  string name = 1;
}

message HelloReply {
  string message = 1;
}
```
Luego **generas código** automáticamente para Python, Java, Go y Node.js.

### 4.3 Streaming
gRPC soporta streaming bidireccional nativo.
*   El cliente sube un archivo (Stream) mientras el servidor va respondiendo progreso (Stream).

## 5. Webhooks (Don't call us, we'll call you)

Las APIs tradicionales (REST) son pasivas. Webhooks son activos.

*   **Sin Webhooks:** Tu servidor pregunta a Stripe cada minuto: "¿Ya pagó el usuario?" (Polling). Ineficiente.
*   **Con Webhooks:** Stripe te llama a TI (`POST https://tu-api.com/stripe-webhook`) cuando el usuario paga.

## 6. Documentación de APIs (OpenAPI / Swagger)

Una API sin documentación no sirve.
**OpenAPI Specification (OAS)** es un estándar YAML/JSON para describir tu API.

```yaml
openapi: 3.0.0
info:
  title: Users API
  version: 1.0.0
paths:
  /users:
    get:
      summary: Returns a list of users.
      responses:
        '200':
          description: A JSON array of user names
```

*   **Herramientas:** Swagger UI lee este YAML y genera una página web interactiva donde puedes probar la API.

## 7. Matriz de Decisión: ¿Cuál uso?

| Criterio | REST | GraphQL | gRPC | SOAP |
| :--- | :--- | :--- | :--- | :--- |
| **Formato** | JSON | JSON | Protobuf (Binario) | XML |
| **Velocidad** | Media | Media | **Extrema** | Lenta |
| **Tipado** | No (Flexible) | **Sí (Schema)** | **Sí (Proto)** | Sí (WSDL) |
| **Apalancamiento** | CRUD simple | Grafos complejos | Microservicios internos | Legacy / Bancos |
| **Consumible por** | Cualquiera | Apps Móviles | Backend-to-Backend | Mainframes |
| **Navegador Web** | Nativo | Librería extra | Requiere Proxy (gRPC-Web) | Difícil |

## 8. Implementación de Referencia: REST (Node.js + Express)

Cómo se ve una API REST profesional hoy en día.

```javascript
const express = require('express');
const app = express();
app.use(express.json());

const users = [];

// GET /users (Collection Resource)
app.get('/users', (req, res) => {
  // Filtrado y Paginación (Best Practice)
  const limit = req.query.limit || 10;
  res.status(200).json(users.slice(0, limit));
});

// POST /users (Create)
app.post('/users', (req, res) => {
  const newUser = { id: Date.now(), ...req.body };
  users.push(newUser);
  // 201 Created + Location Header
  res.status(201)
     .header('Location', `/users/${newUser.id}`)
     .json(newUser);
});

// GET /users/:id (Member Resource)
app.get('/users/:id', (req, res) => {
  const user = users.find(u => u.id == req.params.id);
  if (!user) return res.status(404).json({ error: "User not found" });
  
  // HATEOAS Links
  res.json({
    ...user,
    links: [
      { rel: "self", method: "GET", href: `/users/${user.id}` },
      { rel: "delete", method: "DELETE", href: `/users/${user.id}` }
    ]
  });
});

// HTTP 405 Method Not Allowed
app.all('/users', (req, res) => {
  res.status(405).send("Method Not Allowed");
});
```

## 9. Implementación de Referencia: GraphQL (Apollo Server)

Nótese cómo el **Resolver** sustituye al **Router**.

```javascript
const { ApolloServer, gql } = require('apollo-server');

// 1. Schema (La Forma)
const typeDefs = gql`
  type Book {
    title: String
    author: String
  }

  type Query {
    books: [Book]
    book(title: String): Book
  }
`;

// 2. Data
const books = [
  { title: 'The Awakening', author: 'Kate Chopin' },
  { title: 'City of Glass', author: 'Paul Auster' },
];

// 3. Resolvers (La Lógica)
const resolvers = {
  Query: {
    books: () => books,
    book: (_, args) => books.find(b => b.title === args.title)
  },
};

// 4. Server
const server = new ApolloServer({ typeDefs, resolvers });

server.listen().then(({ url }) => {
  console.log(`🚀  Server ready at ${url}`);
});
```

## 10. Implementación de Referencia: gRPC (Node.js)

Requiere una definición `.proto` y un loader dinámico.

**helloworld.proto**
```protobuf
syntax = "proto3";
package helloworld;
service Greeter {
  rpc SayHello (HelloRequest) returns (HelloReply) {}
}
message HelloRequest {
  string name = 1;
}
message HelloReply {
  string message = 1;
}
```

**server.js**
```javascript
const grpc = require('@grpc/grpc-js');
const protoLoader = require('@grpc/proto-loader');

const packageDefinition = protoLoader.loadSync('helloworld.proto');
const hello_proto = grpc.loadPackageDefinition(packageDefinition).helloworld;

function sayHello(call, callback) {
  callback(null, { message: 'Hello ' + call.request.name });
}

const server = new grpc.Server();
server.addService(hello_proto.Greeter.service, { sayHello: sayHello });
server.bindAsync('0.0.0.0:50051', grpc.ServerCredentials.createInsecure(), () => {
  server.start();
});
```

## 11. Estrategias de Versionado (Cómo no romper clientes)

Tu API va a cambiar. ¿Cómo lo manejas?

### 11.1 URI Versioning (Twitter, Google)
*   `GET /api/v1/tweets`
*   `GET /api/v2/tweets`
*   **Pros:** Explícito, fácil de cachear.
*   **Contras:** Ensucia la URL.

### 11.2 Header Versioning (GitHub, Stripe)
*   `GET /tweets`
*   Header: `Accept: application/vnd.myapi.v2+json`
*   **Pros:** URL limpia.
*   **Contras:** Difícil de probar en el navegador.

## 12. Seguridad en APIs (Lo Mínimo Indispensable)

### 12.1 Rate Limiting (Token Bucket)
Evita que un script te tire el servidor.
*   Uso: `express-rate-limit`.
*   Regla: "Max 100 requests por 15 minutos por IP".
*   Retorno: `HTTP 429 Too Many Requests`.

### 12.2 CORS (Cross-Origin Resource Sharing)
Por defecto, el navegador BLOQUEA peticiones de `midominio.com` a `api.otro.com`.
*   El servidor debe enviar header: `Access-Control-Allow-Origin: *`.

### 12.3 JWT (JSON Web Tokens)
El estándar de Auth Stateless.
*   **Header:** Algoritmo (`HS256`).
*   **Payload:** Datos (`user_id: 123`, `exp: 1710000000`).
*   **Signature:** Firma criptográfica para evitar tampering.

## 13. Manejo de Errores (RFC 7807)

No inventes formatos de error (`{"err": "bad", "code": 99}`). Usa el estándar **Problem Details for HTTP APIs**.

```json
HTTP/1.1 403 Forbidden
Content-Type: application/problem+json

{
  "type": "https://example.com/probs/out-of-credit",
  "title": "You do not have enough credit.",
  "detail": "Your current balance is 30, but that costs 50.",
  "instance": "/account/12345/msgs/abc",
  "balance": 30,
  "accounts": ["/account/12345", "/account/67890"]
}
```

*   **type:** URI única del tipo de error.
*   **title:** Título humano corto.
*   **detail:** Explicación específica.
*   **instance:** Dónde ocurrió.

## 14. AsyncAPI (Documentando Eventos)

OpenAPI es para REST. **AsyncAPI** es para Kafka/RabbitMQ.

```yaml
asyncapi: 2.0.0
info:
  title: Streetlights API
  version: 1.0.0
channels:
  light/measured:
    publish:
      message:
        payload:
          type: object
          properties:
            id:
              type: integer
            lumens:
              type: integer
```

*   Define **Canales** (Topics) en lugar de Paths (URLs).
*   Define **Publish/Subscribe** en lugar de GET/POST.

## 15. Cheat Sheet de HTTP Status Codes (Los Útiles)

Hay 63 códigos. Solo necesitas estos 10:

### 2xx: Éxito
*   **200 OK:** Todo bien (Sync).
*   **201 Created:** Recurso creado (`POST`). Devuelve `Location`.
*   **202 Accepted:** Todo bien, pero lo procesaré después (Async).
*   **204 No Content:** Todo bien, pero no hay nada que devolver (`DELETE` exitoso).

### 3xx: Redirección
*   **301 Moved Permanently:** "Cambié de dominio, actualiza tus bookmarks". (SEO).
*   **304 Not Modified:** "Tu caché sigue siendo válida, no te envío datos".

### 4xx: Error del Cliente (Tu culpa)
*   **400 Bad Request:** JSON mal formado o validación fallida.
*   **401 Unauthorized:** "¿Quién eres?" (Falta Token).
*   **403 Forbidden:** "¿Quién eres y por qué quieres entrar aquí?" (Tienes Token, pero no permisos).
*   **404 Not Found:** "No existe".
*   **429 Too Many Requests:** "Cálmate".

### 5xx: Error del Servidor (Mi culpa)
*   **500 Internal Server Error:** NullPointerException no manejada.
*   **502 Bad Gateway:** El servidor Node.js se murió y Nginx no sabe qué hacer.
*   **503 Service Unavailable:** Estoy en mantenimiento o sobrecargado.

## 16. Testing de Servicios (QA Automatizado)

No pruebes manual con Postman siempre. Automatiza.

### 16.1 Supertest + Jest (Integration Tests)
Prueba tu API completa sin levantar el servidor en el puerto 3000.

```javascript
const request = require('supertest');
const app = require('./app');

describe('GET /users', () => {
  it('responds with json', async () => {
    const res = await request(app)
      .get('/users')
      .set('Accept', 'application/json')
      .expect('Content-Type', /json/)
      .expect(200);
      
    expect(res.body).toHaveLength(10);
  });
});
```

### 16.2 k6 (Load Testing)
¿Tu API aguanta 1000 usuarios?
Script en Javascript que simula carga masiva.

```javascript
import http from 'k6/http';
import { sleep } from 'k6';

export default function () {
  http.get('https://mi-api.com/users');
  sleep(1);
}
```
*   Ejecuta: `k6 run --vus 100 --duration 30s script.js`.
*   Resultado: "99% de los requests tardaron < 200ms".

## 17. Real-Time Web (Más allá de REST)

REST es "Petición-Respuesta" (Cliente habla, Servidor responde). Pero, ¿y si el servidor quiere hablar?

### 17.1 WebSockets (Bidireccional)
*   Un túnel TCP persistente.
*   **Uso:** Chats, Juegos Multiplayer, Cotizaciones de Bolsa.
*   **Pros:** Latencia ultra baja.
*   **Contras:** Difícil de escalar (Stateful connection). Si tienes 1 millón de usuarios, necesitas 1 millón de conexiones abiertas.

### 17.2 Server-Sent Events (SSE)
*   **Unidireccional:** El servidor envía datos al cliente (como una radio), pero el cliente no responde por ahí.
*   **Uso:** Notificaciones de Facebook, Feed de Twitter.
*   **Ventaja:** Usa HTTP estándar, más fácil que WebSockets.

---

## 18. El Futuro: HTTP/3 (QUIC)

HTTP/2 arregló muchos problemas, pero seguía usando TCP.
*   **Problema de TCP:** Si se pierde un paquete, TODO se detiene (Head-of-Line Blocking).
*   **Solución HTTP/3:** Usa **UDP** (el protocolo "inseguro" de los videojuegos).
*   Le añade una capa de confiabilidad y cifrado (TLS 1.3) integrada.
*   **Resultado:** Carga instantánea en conexiones móviles inestables (4G/5G).
